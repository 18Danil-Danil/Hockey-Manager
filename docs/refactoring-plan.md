# План безопасного разделения Hockey Manager

## Исходное состояние (проверено 2026-11-09)

- Основная ветка: `main`.
- Рабочая ветка для рефакторинга: `refactoring` (создана от `main`).
- Основной файл: `script.js`, 4 654 строки.
- `index.html` подключает `script.js` обычным классическим тегом `<script src="script.js"></script>`.
- `style.css` содержит стили интерфейса.
- В коде есть крупные самостоятельные блоки: данные клубов, RNG/утилиты, игроки и здоровье, новости/почта, штаб и академия, составы/звенья, календарь и лига, симуляция матчей, экономика, трансферы, развитие игроков, таблица и плей-офф, Live-движок/Canvas, интерфейс, сохранения и запуск.
- Найдено много верхнеуровневых объявлений и функций. Точный перенос требует анализа зависимостей, а не простого разрезания по комментариям.

## Главные риски

1. Интерфейс содержит обработчики событий, которым могут быть нужны функции из глобальной области видимости.
2. Разные игровые системы обращаются к общему состоянию игры (в коде есть отдельный блок глобального состояния).
3. Сохранения зависят от структуры данных и имён полей; рефакторинг не должен менять формат сохранения.
4. Порядок инициализации важен: данные и функции должны быть доступны до запуска новой игры и первого render.
5. Вынесение функций в ES-модули меняет область видимости. Нельзя просто добавить `type="module"` и переместить функции без адаптации публичных обработчиков.

## Предлагаемый порядок

### Этап 0 — страховка и карта (текущий)
- Сохранить `main` без изменений.
- Работать только в ветке `refactoring`.
- Составить карту блоков и зависимостей.
- Не менять игровую механику и формат сохранений.

### Этап 1 — подготовка модульной оболочки
- Определить публичные функции, вызываемые из HTML-атрибутов и динамически созданных элементов.
- Определить владельца общего состояния и порядок инициализации.
- Выбрать переходный способ экспорта функций, чтобы существующий UI не потерял обработчики.
- Добавить простую проверку синтаксиса/загрузки, если она совместима с текущим статическим проектом.

### Этап 2 — перенос низкорисковых блоков
- В первую очередь вынести константы/данные клубов и чистые утилиты/RNG.
- Затем переносить независимые блоки небольшими порциями.
- После каждого переноса проверять импорты, экспорты, загрузку страницы, запуск новой игры и загрузку сохранения.

### Этап 3 — игровые системы
- По отдельности вынести игроков, составы, матчи, лигу/плей-офф, финансы, трансферы, академию и развитие.
- Не менять баланс, алгоритмы, названия полей и формат сохранений в рамках структурного переноса.

### Этап 4 — интерфейс и финальная проверка
- Разделить UI по экранам/модальным окнам.
- Проверить все основные сценарии: новая игра, выбор клуба, календарь, симуляция матча, Live-матч, трансферы, финансы, сохранение и загрузка.
- Только после проверки подготовить изменения к переносу в `main`.

## Правила безопасности

- Не выполнять массовое автоматическое разрезание файла.
- Не удалять старый код, пока его замена не проверена.
- Не менять `main` в ходе работы.
- Каждый логический этап фиксировать отдельным коммитом в `refactoring`.
- При обнаружении неопределённости сначала анализировать зависимости, а не угадывать.
